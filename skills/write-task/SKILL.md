# 编写实现计划书

将当前会话压缩为仓库根目录下的 `TASK.md`, 供新的 agent 会话直接执行.

这是一次实现任务交接: 保存执行所需的代码事实, 设计决定, 任务顺序和验证标准.

## 执行步骤

### 1. 回顾

基于当前会话和已经完成的代码探索整理任务上下文.

- 必要时重新读取关键代码, 以确认可能过时或不确定的事实; 不要重新进行无目的的全面探索.
- 区分已验证的代码事实, 已经达成的设计决定和仍未确认的假设.
- 保留新会话难以低成本重新获得的信息: 关键入口, 调用关系, 职责边界, 约束, 设计取舍和测试基础.

完成标准: 新的 agent 无需读取原会话, 也无需重复大范围探索, 即可理解任务并开始实施.

### 2. 计划

按照依赖关系将实现组织为少量阶段.

- 每个阶段表达一个明确的中间目标.
- 阶段内的工作全部写为未勾选的 checklist.
- 每个 checklist 项表示一个可完成, 可验证的结果.
- 在有助于定位时注明主要文件和符号.
- 避免逐行实现指令和大段代码. 仅当类型, 协议, 状态机或数据结构本身就是已确定的设计时, 保留最小必要形状.
- 每个阶段给出完成条件, 使后续 agent 能判断是否可以进入下一阶段.
- 验证项同样使用 checklist, 供执行过程中逐项勾选.

完成标准: 每项验收目标都有对应的实施任务和验证方式, 任务顺序不存在未声明的依赖.

### 3. 编写

使用下方模板创建或替换仓库根目录的 `TASK.md`.

- 使用项目已有的领域术语.
- 只记录最终方案.
- 无法确认但不阻塞实施的内容应明确标为假设.
- 所有进度项初始保持未勾选.

完成标准: `TASK.md` 自包含, 精炼, 可执行, 可验证, 并且没有隐藏的阻塞问题.
