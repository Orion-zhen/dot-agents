# development

采用人在回路的开发方式. 先理解用户意图并调查代码仓库, 再与用户讨论执行计划. 计划确认后完成实现和验证. 计划失效, 遇到阻碍或需要用户取舍时再次暂停. 尊重用户指定的模式. 规划, 原型或审查本身可能就是最终交付. 除非用户明确要求, 否则不要自动进入实现阶段.

## 理解与计划

- 阅读相关代码, 测试, 文档和项目约定.
- 明确目标行为, 约束, 非目标和完成标准.
- 能从环境中确认的事实自行确认, 不把调查工作转交给用户.
- 默认遵循现有风格和模式, 除非当前任务提供了改变它们的证据.
- 只有无需实质调查或规划的局部修改可以直接实现.
- 多步骤, 跨边界, 高风险或存在实质歧义时, 使用 `read` 工具阅读 `skill://development/references/planning.md`.
- 可以使用一次性原型消除关键未知, 但不要在方案确认前将原型扩展为正式实现.
- 收集到足够信息后, 暂停并向用户报告调查结果或执行计划.

## 工程实现

代码设计追求较高收益和局部性. 调用方只需理解精简的接口. 实现细节, 不变量和变化应集中在内部.

- 从调用方需要的行为和必须了解的事实出发设计接口. 将因同一原因而变化的代码放在一起.
- 优先复用项目已有能力. 新增依赖或自行实现前, 比较维护成本, 供应链风险, 兼容性和实现复杂度. 依赖接口发生变化时, 先确认当前版本提供的能力.
- 平衡重复代码和抽象成本. 只在真实变化点, 有意义的测试边界或需要隐藏重复复杂性时引入抽象. 单一假想实现不足以证明抽象的必要性.
- 使用删除测试判断一层抽象是否有价值. 如果删除后只是把复杂度转移给调用方, 保留该层. 如果调用方变化很小, 该层可能只是透传结构.
- 保持模块职责清晰. 避免职责混杂的巨型文件, 也避免只包装一次调用的无意义模块.
- 对重要接口至少比较两种设计, 再权衡调用成本, 局部性, 可测试性和未来变更成本.
- 控制修改范围. 避免预设框架, 过早扩展点, 无关清理和推测性改进.
- 只在任务暴露出具体问题时重构, 例如策略重复, 知识分散, 接口泄露, 修改扩散或无法通过行为测试. 结构性修改应贴近触发它的任务. 必要时将结构修改和行为修改分开, 以便审查和定位问题.

### 必要性驱动的防御代码

防御代码必须由真实边界, 明确的故障语义或实际证据支撑. 审查兜底时同时考虑触发概率和失败影响. 低概率本身不能证明代码应该保留或删除.

- 每个不变量只由一层负责. 在未经过验证的输入, 配置或外部协议进入系统的边界验证结构和取值范围. 下游信任已经建立的保证, 只检查本层独有的领域规则和安全约束.
- 通过非空元组, 判别联合, 必需字段, 重载或泛型返回值表达不变量. 不要用可选字段, 默认值或事后检查拼凑合法状态.
- 意外失败默认向上传播. 不要把依赖错误或内部不变量破坏转换成 `undefined`, 空结果, 默认值或另一种看似成功的执行路径.
- 只在以下情况捕获错误: 在公开边界转换错误, 清理资源并保留原始失败, 为明确声明的非关键增强提供降级, 或对已知平台瞬态错误执行有界重试.
- 删除当前接口, 类型和生命周期无法触发的分支. 删除没有现实调用方的配置项, 兼容层, 能力探测和备用实现. 不要保留缺少实际需求或测量依据的缓存和重试策略.
- 生命周期一致的上下文和依赖应在构造边界绑定一次. 不要让每一层重复接收, 合并和兜底同一状态.
- 保留承担独立安全职责的保护, 包括访问边界, 路径安全, 并发修改检测, 取消, 资源清理以及大小和资源限制. 这些保护不能仅因触发概率低而删除.
- 新增或保留兜底前, 确认触发来源, 上游保证, 违规后果, 公开语义和现实证据. 如果上游已经排除该状态, 且当前层不承担独立保护职责, 应删除兜底, 将校验移至真实边界或收紧类型.
- 测试公开支持的行为和真实边界. 不要绕过公开类型或参数结构, 人为构造内部非法状态来要求每一层恢复. 保留的兜底应有明确的触发条件和结果语义.

## 执行与反馈

- 用户确认或调整计划后, 自主决定常规实现细节并完成约定工作, 不重复请求确认.
- 优先交付能产生可观察结果的完整功能块, 包含必需的代码, 测试, 配置和文档.
- 尽早消除关键不确定性.
- 合并同一文件或功能切片中已经确定的兼容修改, 避免将已知修改拆成多轮小幅编辑.
- 先运行最快的相关检查. 完成一个连贯功能切片后再扩大验证范围.
- 建立针对目标行为的快速反馈. 测试策略不明显或验证范围较复杂时, 使用 `read` 工具阅读 `skill://development/references/testing.md`.
- 如果工作转变为排查错误和寻找原因, 使用 debugging skill. 先建立证据, 再修改代码.

仅在以下情况暂停执行并重新询问用户:

- 新证据使已确认的计划不再成立.
- 必须改变约定的行为, 范围或设计.
- 出现需要用户决定的重要取舍或风险.
- 遇到无法自行解决的阻碍, 或重复尝试仍未取得进展.

暂停时说明问题, 已确认的证据, 可选方案和建议, 然后等待用户回应.

## 代码审查

- 从设计意图完成情况和代码工程质量两个角度审查.
- 审查发现和外部审查意见都应由实际代码证据支持.
- 审查任务不自动进入修改阶段.
- 对于审查任务或较大改动, 使用 `read` 工具阅读 `skill://development/references/review.md`.

## 完成条件

满足以下要求后停止:

- 所需行为或交付物已覆盖.
- 已在最终状态上运行相关测试验证.
- 修改范围受控, 没有遗留原型或调试内容.
- 已报告修改内容, 验证证据, 未验证部分和剩余风险.

不要追加推测性清理或无关改进.
