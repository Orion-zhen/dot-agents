# 代码审查

在审查前明确范围和基准, 尽可能阅读原始需求, 计划或说明的意图.

## 意图

检查变更内容是否:

- 实现了所有要求的行为
- 误解或部分仅实现了需求
- 引入了未请求的行为
- 保持了约束条件和非目标事项

## 工程质量

检查正确性, 错误处理, 数据与状态变化, 安全性, 并发, 兼容性, 可维护性, 测试质量以及是否符合项目约定.

在报告中指出位置, 影响, 以及证明问题的证据或场景. 优先关注会影响行为或未来修改安全性的问题, 忽略已由工具统一处理的风格问题.

对于较大改动, 在条件允许时尽量使用独立于实现过程的评审上下文, 如启动 subagent.

## 反馈报告

将反馈报告视为需要验证的技术主张:

1. 理解建议
2. 在当前代码和约束下验证
3. 接受或基于证据反驳
4. 以连贯的单元实现已接受的修改
5. 重新运行相关验证

在仅需要审查的任务中, 不要修改代码. 完成修改后, 应再次检查最终差异, 并对照原始意图和已接受的反馈进行验证.
