# 设计与重构

代码设计应追求杠杆与局部性: 调用方秩序理解较小接口, 而实现细节, 不变量和变化则集中在内部.

优先复用项目已有能力. 新增依赖或自行实现时, 比较维护, 供应链, 兼容性和复杂度成本.

## 设计理念

- 平衡重复代码与抽象功能. 避免脆弱的, 仅有一两个地方复用的抽象. 在没有达到抽出稳定的可复用模块时, 允许存在少量重复代码.
- 避免超巨型单体文件. 代码文件应该职责边界清晰, 模块化好.
- 当依赖项版本更新时, 可以根据 API 的改动, 思考如何能利用新版的接口来简化当前代码的执行链路, 或者让当前代码的实现更加健壮.

## 塑造变更

从调用方需要的行为和必须了解的事实出发, 接口应小于其隐藏的复杂度. 将因同一原因而变化的代码放在一起. 仅在真实变化点, 有意义的测试边界或需要隐藏重复复杂性时引入抽象. 单一假想未来实现不足以证明抽象的必要性.

采用"删除测试", 如果移除某层只是把复杂度转移到调用方, 则该层有价值; 如果变化很小, 则可能只是透传结构.

对于重要接口, 应至少考虑两种不同的设计, 再比较调用成本, 局部性, 可测试性和未来变更成本.

## 基于证据重构

当暴露出具体问题时, 执行重构. 例如:

- 策略重复
- 知识分散
- 接口泄露或过大
- 修改需要触及过多无关位置
- 无法通过行为进行测试

结构性修改应贴近触发它的任务, 但在必要时与行为修改分离, 以避免造成审查困难或问题难以定位.

默认遵循现有架构, 除非当前任务提供了改变它的证据. 避免预设框架, 过早扩展点和与目标无关的清理.
